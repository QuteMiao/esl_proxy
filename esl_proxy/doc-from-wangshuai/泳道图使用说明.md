# 泳道图（Swimlane）使用说明

把一次运行画成时间线：**每个 AI core 槽位一条泳道**，横轴是真实流逝时间，
上面是一个个任务块。用来肉眼看清「谁在等谁、核有没有闲着、ED 到底赚没赚到」。

> 名词：**泳道图**指按时间轴把并行参与者各画一行的图；**Perfetto** 是一个网页版
> 时间线查看器（<https://ui.perfetto.dev/>），把文件拖进去就能看，不用装软件。

---

## 1. 三条命令跑通

```bash
cd esl_proxy                                   # 有 Makefile 的那层
make swimlane ED_ENABLE=1 SWIMLANE_DIR=report/ed_on
# 打开 https://ui.perfetto.dev/ 把 report/ed_on/merged_swimlane.json 拖进去
```

想对照 ED（Early Dispatch，提前派发）开关的差别，就再跑一次：

```bash
make swimlane ED_ENABLE=0 SWIMLANE_DIR=report/ed_off
```

`make swimlane` 做了三件事：用 `SWIMLANE=1` 重新编译 → 跑一次 → 转成 Perfetto 文件，
同时在终端打一份统计摘要。

### 为什么这个目标会偷偷改 `EXEC_DURATION_SCALE`

`EXEC_DURATION_SCALE`（模拟执行时长的缩放因子）默认是 10000，意思是把任务的
原始 cycle 数除以 10000 再当作 tick 数跑。默认值下几乎每个任务都只剩 1 tick，
**执行段会退化成零宽**，图上只剩排队结构，看不到核占用。所以 `make swimlane`
把它默认改成 200。想按真实比例看就显式覆盖：

```bash
make swimlane EXEC_DURATION_SCALE=10000
```

实测差别（同一个 case）：scale=10000 时核忙碌率只有 2%，scale=200 时是 88%。

## 2. 图上有什么

Perfetto 左侧会出现六组泳道：

| 分组 | 一行代表 | 内容 |
| --- | --- | --- |
| `1 Orchestrator` | 编排线程 | 整段建图的包络 |
| `2 Cutter` | 解依赖线程 | `cut_commit`（挂边）、`cut_resolve`（递减依赖） |
| `3 Dispatcher` | 派发线程 | `disp_drain`（收完成）、`send_cube/vector/mix`、`disp_ed`（投机占槽） |
| `4 Core (run only)` | 一个逻辑核 `CUBE_07` | **只画真正执行段**，看核占用就看这层 |
| `5 Slot detail` | 一个槽位 `CUBE_07/s1` | 四段全画，钻细节用 |
| `6 Task marks` | 一类瞬时事件 | `ready`（依赖归零）、`notify_h1/h2`（敲门铃） |

另有两条 counter（计数曲线）轨：`cores_running`（同时在跑的核数）、
`slots_gated`（同时被 ED 占住的槽位数）。

### 一个任务被拆成四段

| 段 | 区间 | 含义 |
| --- | --- | --- |
| `gated` | stage → 开闸 | ED 已占住槽位，但门铃没响，不能跑（normal 路径没有这段） |
| `wait` | 开闸/发布 → 认领 | 已经可执行，但这个核正忙着别的槽位 |
| `run` | 认领 → 完成 | executor 真正在 tick 倒计时 |
| `fin` | 完成 → 被看见 | dispatcher 下一轮 drain 才收到 done 位 |

鼠标悬停任意一块会显示 `task_id / path / core / slot / blocks` 和四段各自的微秒数。

### 为什么要分 Core 和 Slot 两层

一个核有 `AIC_OSTD` 个槽位（默认 2）。ED 把任务塞进某核的空闲槽位等门铃时，
**该核另一个槽位可能正在跑别的任务**——两段时间是重叠的。而 Perfetto 要求同一条
轨道上的块要么不相交、要么严格嵌套，重叠会直接报错。所以细节层按槽位切。

Core 层只画 `run` 段就不会有这个问题：executor 每个核同时只认领一个槽位
（`executor_t::idx` 保证），天然互斥。

## 3. 该看什么

1. **ED 有没有吃掉预装载位**：`slots_gated` 曲线抬起来的那段，去 Slot 层看同一个核的
   另一条 `sX` 泳道是不是正忙。是的话，这次 ED 就是拿本可预装载 normal 任务的名额换的。
2. **开闸够不够快**：`notify_h2` 瞬时事件到对应任务 `gated` 段结束之间的距离。
3. **核在不在闲**：`cores_running` 曲线塌下去的时段，回头看 Dispatcher 那一行是不是也空着——
   空着说明没任务可派（前面卡在依赖），忙着说明派发本身是瓶颈。
4. **编排拖不拖后腿**：Orchestrator 那条长条结束之后，Core 层还在不在持续有任务。

终端摘要里的 `pub->run wait mean` 和 `ED gated mean` 是上面第 1、3 条的数字版。

---

## 4. 重要限制：这个开关下的性能数字不可用

`SWIMLANE=1` 会在热路径插入时钟读取和内存写入，还会改变
`dispatch` / `executor` 的代码布局与栈帧大小。仓库里已经有明确教训：
`dispatch_worker` 的栈帧涨 48 字节就让 makespan 漂了 9%~13%
（见 `dispatch.c` 里 `dispatch_finish` 上方那段注释）。

所以：

- **看结构** → `SWIMLANE=1`
- **测性能** → `SWIMLANE=0`（默认值），用 `scripts/ed_paired_ab.py` 那套

两者不要混着得结论。

## 5. 想调的旋钮

| 在哪 | 名字 | 作用 |
| --- | --- | --- |
| make 变量 | `SWIMLANE=0/1` | 总开关，默认 0 |
| make 变量 | `SWIMLANE_DIR` | 产物目录，默认 `report` |
| 环境变量 | `SWIMLANE_JSON` | 直接指定原始 JSON 路径，优先于 `SWIMLANE_DIR` |
| `swimlane.h` | `SWIM_MAX_TASKS` 等 | 缓冲上限。溢出只丢新记录并在收尾打印，不会崩 |

如果收尾看到 `dropped ...`，按提示调大对应的 `SWIM_MAX_*` 重编即可。

## 6. 两个产物文件

| 文件 | 谁写的 | 内容 |
| --- | --- | --- |
| `swimlane_records.json` | 进程收尾时 C 侧落盘 | 原始记录，三条流（tasks / phases / marks） |
| `merged_swimlane.json` | `tools/swimlane_to_perfetto.py` | Perfetto 能直接打开的 trace |
| `swimlane.png` | `tools/swimlane_png.py` | 速览图，贴文档 / 发人用 |

`swimlane_png.py` 只用标准库画 PNG，不需要装 matplotlib。它不能缩放不能点，
正经看图还是用 Perfetto，它解决的是"不开浏览器先瞄一眼整体形状"：

```bash
# 默认画出全部 120 条硬件泳道，没派到活的核会留空——这通常是第一眼要看的
python3 ../tools/swimlane_png.py report/demo/swimlane_records.json

# 只看用到的核，并放大到第 140~300 微秒（时间以第一个任务开跑为 0 点）
python3 ../tools/swimlane_png.py report/demo/swimlane_records.json \
    --used-only --from-us 140 --to-us 300 --lane-height 16
```

转换器是纯后处理，改了配色或分组不用重跑负载，对着同一份原始 JSON 再转一次就行：

```bash
python3 ../tools/swimlane_to_perfetto.py report/ed_on/swimlane_records.json
python3 ../tools/swimlane_to_perfetto.py report/ed_on/swimlane_records.json --summary-only
```

## 7. 打点都在哪（改代码时对照）

| 文件 | 打点 |
| --- | --- |
| `dispatch.c::send_task` | normal 路径 `pub`；`disp_send` 阶段条 |
| `dispatch.c::drain_completed_snapshot` | `finish` 回填；`disp_drain` 阶段条 |
| `dispatch.c::dispatch` | `disp_ed` 阶段条 |
| `early_dispatch.c::try_early_dispatch` | ED 路径 `stage` |
| `early_dispatch.c::ed_notify_once` | `notify_h1/h2` 瞬时事件 |
| `ed_gate.h::ed_poll_doorbell` | ED 开闸，`gated` 段终点 |
| `executor.c` 认领分支 | `run` 起点 |
| `executor.c::complete_slot` | `run` 终点，整条记录落缓冲 |
| `cutter.c::resolve_dep` | `ready` 瞬时事件 |
| `cutter.c::deal_completed_queue` | `cut_commit` / `cut_resolve` 阶段条 |
| `main.c` | `swim_init` / 编排包络 / `swim_dump` |

两条必须守住的规矩：

1. **阶段条只在真干了活时才落**（`complete_cnt>0`、`sent>0`、staged>0）。
   dispatch 主循环是百万次量级，每轮都记会把内存和 Perfetto 一起撑爆；
   空转由相邻两条记录之间的空隙表示。
2. **任务打点必须早于 `slot_state` 发布**。executor 在另一个线程，槽位一发布出去
   下一拍就可能被认领甚至跑完，晚写会丢点。
